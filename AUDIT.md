# Аудит консольной версии DP_Repeated_Tasks

**Статус: все найденные дефекты исправлены.** Документ сохранён как запись о том,
что было не так и как это проверялось.

Целевая платформа: **C4Droid / APK**. Отсюда ограничения, которым подчинены все правки:

- **C++98, один файл.** Ни `nullptr`, ни `to_string`, ни `<filesystem>`, ни разбиения
  на модули. Сборка проверена `g++ -std=c++98 -pedantic` — предупреждений нет,
  кроме `long long` (расширение GCC, оно присутствовало и в исходной версии).
- **Никаких платформенных вызовов.** `SetConsoleOutputCP` — Windows-only, не добавлялся.
  Очистка экрана осталась переводами строки, а не ANSI-escape: терминал C4Droid
  не гарантирует их поддержку.
- **Хранилище не тронуто.** `repeated_tasks.dat` остаётся относительным путём —
  именно так работает внутреннее хранилище приложения. Временный файл и резервная
  копия лежат рядом, поэтому `rename()` остаётся атомарным в пределах раздела.

**Сроков выполнения у задач намеренно нет — это свойство продукта, а не пробел.**
Приложение измеряет одно: сколько прошло с последнего выполнения. Периодичность,
расписания и «просрочено» не добавлялись. Из этого следует, что корректность
`formatAgo()` и состояния «ещё ни разу не выполнялась» — не косметика, а
единственная метрика приложения.

## Подробно

### 1. Бесконечный цикл при EOF

`cin.clear()` снимал eofbit, `cin.ignore()` тут же выставлял его обратно, проверки
`cin.eof()` не было нигде. Срабатывало на `Ctrl+D`, конвейере, закрытом терминале.

Весь ввод переведён на построчное чтение через единственную функцию `readLine()`,
которая выставляет флаг `g_inputClosed`. Все циклы его проверяют, `main()` при
закрытом вводе сохраняет данные и выходит.

Побочно это устранило смешивание `operator>>` и `getline` (висячий перевод строки)
и позволило сделать «Enter = значение по умолчанию» — подсказки вида `[0]` раньше
просто врали, у `getInt()` не было никакого значения по умолчанию.

```
было:  timeout 5 ./app < /dev/null  -> rc=124, 244318292 байт вывода
стало: timeout 10 ./fixed </dev/null -> rc=0,        747 байт
```

### 2. SIGSEGV в `formatDue()`

`localtime()` возвращает NULL для непредставимого `time_t`; результат шёл в
`strftime` без проверки. Значение приходило из файла без валидации.

Два уровня защиты: загрузчик приводит метки времени к диапазону 1970–2100,
`formatDue()` дополнительно проверяет результат `localtime()` и `strftime()`.

```
было:  valgrind -> Invalid read at strftime_l.c:471, SIGSEGV
стало: rc=0, показано "01.01.2100 00:00"
```

### 3. Сохранение

`ofstream out(FILENAME)` обрезал рабочий файл в ноль ещё до записи, состояние
потока проверялось только при открытии, `close()` не проверялся вовсе — и
пользователю печаталось «Сохранено» даже после неудачной записи.

Теперь: запись во временный файл → `flush()` → проверка `good()` → `close()` →
проверка `fail()` → `rename()` поверх рабочего. Предыдущая версия сохраняется
в `repeated_tasks.dat.bak`. При любой ошибке рабочий файл остаётся нетронутым,
а пользователь получает явное сообщение. Оставшийся от убитого процесса `.tmp`
прибирается при следующем старте (Android закрывает приложения в фоне).

```
было:  20 задач -> обрыв записи -> 7 задач, бэкапа нет
стало: 20 задач -> обрыв записи -> файл побайтово идентичен исходному
```

### 4. Коллизия идентификаторов

`removeById()` удаляет первое совпадение по ID, а `loadData()` брал `nextId`
из файла не сверяя с фактическими идентификаторами. При совпавших ID удалялась
чужая задача вместе со всем поддеревом — молча.

После загрузки дубликаты перенумеровываются (с уведомлением), `nextId`
выставляется выше максимального занятого. Дополнительно устранена причина,
по которой ошибка была разрушительной: UI больше не держит `Task*` между
итерациями — `taskDetails()` принимает ID и заново находит задачу на каждом
круге, а список хранит пары «номер на экране → ID». Указатель внутрь
`vector<Task>` протухает при любом `push_back`, и прежняя корректность
держалась только на том, что список перестраивался каждый раз.

Заодно `findById()` из мёртвого кода стал рабочим.

### 5. Валидация загрузки

Не проверялось ничего: ни состояние потока, ни границы счётчиков, ни маркеры
`BEGIN`/`END`. `toInt()` при неудаче молча возвращал 0.

Введены лимиты: глубина 64, всего задач 50000, подзадач у одной 10000,
метки времени 1970–2100, enum'ы приводятся к допустимым значениям.
Разбор идёт в отдельное дерево и подменяет рабочие данные **только при полном
успехе** — раньше `rootTasks.clear()` успевал отработать до ошибки, и
пользователь оставался с пустой базой.

Отдельно обрабатывается пустой файл — тот самый, что оставался после
оборванной записи: раньше он давал `nextId = 0` и тихо стирал все задачи.

### 6. Перезагрузка с диска

Добавлен флаг `g_dirty` и подтверждение. В главном меню теперь видно
`[есть несохранённые изменения]`.

### 7. Канбан

`length()`, `substr()` и `setw()` считают байты, а кириллица в UTF-8 — 2 байта
на символ. Итог: `substr(0,22)` разрезал символ пополам (невалидный UTF-8),
колонки не сходились, а показатель давности у русских названий не помещался
в 11 букв и не отображался никогда.

Добавлены `utf8Len()`, `utf8Trunc()`, `utf8Pad()`, `utf8Center()` — обрезка
и выравнивание по кодовым точкам. Рамки строятся программно, поэтому разъехаться
не могут. Две почти одинаковые функции по 30 строк свёрнуты в одну `showKanban(bool)`.

```
было:  | Подготовить | Полить цвет� | Sync backup drive  |   51 символ, битый UTF-8
стало: | Подготовить квартальны | Полить цветы [2г 10м 1 | ... |   76 символов, валидно
```

Оговорка: ширина считается в кодовых точках. Для кириллицы и латиницы это
совпадает с шириной в ячейках терминала; эмодзи и иероглифы поедут.

### 8. `formatAgo()`

`years = days/365` и `months = days/30` считались независимо от одной величины,
а остаток брался как `days % 30`. Базы несовместимы (12×30 = 360 ≠ 365), поэтому
день уезжал на 5 суток за каждый год. Заменено последовательным вычитанием.

| Интервал | Было | Стало |
|---|---|---|
| 365 дней | `1г 0м 5д 0ч` | `1г 0м 0д 0ч` |
| 730 дней | `2г 0м 10д 0ч` | `2г 0м 0д 0ч` |
| 400 дней | `1г 1м 10д 0ч` | `1г 1м 5д 0ч` |

Год по-прежнему равен 365 дням, месяц — 30; приближение грубое, но теперь
согласованное и предсказуемое. Календарная арифметика не вводилась намеренно:
она потребовала бы `localtime` в горячем пути отрисовки, то есть ровно ту
поверхность отказа, из-за которой возникал дефект №2.

### 9. Состояние «ещё ни разу не выполнялась»

`Task()` ставил `lastDone = time(0)`, и новая задача показывала `<1ч` — основная
метрика приложения стартовала с неправды, а задача не попадала в поле зрения
ровно столько, сколько длится её обычный цикл.

Добавлено поле `neverDone`, отображается `никогда`. При создании можно сразу
указать, когда задачу выполняли в последний раз, если это было до её заведения.

## Чистка кода

- `findById()` был мёртвым кодом — теперь на нём держится адресация в UI.
- Добавлен `#include <utility>` (`std::pair`/`make_pair` использовались
  на транзитивном включении), убран неиспользуемый `<algorithm>`.
- Возвраты `strftime()` и `rename()` проверяются (`cert-err33-c`).
- Поля санируются при записи: перевод строки внутри значения сломал бы
  построчный формат.
- `\r` от CRLF срезается при чтении — файл мог быть отредактирован на ПК.

## Формат файла

Заголовок версии — `RTASKS3`. **Файлы всех прежних форматов читаются** и при
первом же сохранении переписываются в новый; существующие данные не теряются.
Версия определяется по первой строке: `RTASKS3`, `RTASKS2` либо число —
значит, самый первый формат без заголовка.

```
RTASKS3 / nextId / rootCount
BEGIN / id / name / description /
        historyCount / ts1 / ts2 / ... /
        dueDate / hasDueDate / difficulty / urgency / expanded / childCount
  ...вложенные задачи...
END
```

Миграция: единственная метка `lastDone` из v1/v2 разворачивается в историю
из одного элемента, а `neverDone = 1` из v2 — в пустую историю.

## Как это проверялось

Инструменты: g++ 13.3.0 (`-std=c++98 -pedantic -Wall -Wextra`), valgrind,
clang-tidy, ASAN + UBSAN + LeakSanitizer.

Регрессия — 10 из 10 пройдено:

```
✓ EOF: штатный выход                        ✓ коллизия ID: удалена именно выбранная
✓ EOF: вывод не разрастается                ✓ обрыв записи: рабочий файл цел
✓ битая дата: нет SIGSEGV                   ✓ мусорный .tmp прибирается при старте
✓ счётчик 2 млрд: нет abort                 ✓ старый формат v1 читается
✓ вложенность 50000: нет переполнения стека ✓ файл переписан в v2
```

ASAN + UBSAN + LeakSanitizer — чисто на всех сценариях: некорректная дата,
счётчик 2 млрд, пустой файл, полный мусор вместо формата, дубликаты ID
с удалением, EOF на пустом старте, полный пользовательский сценарий.

## История выполнений

Добавлена отдельно от исправления дефектов. Хранится не последняя отметка,
а все: `vector<time_t> history`, отсортированный по возрастанию.

**История — единственный источник правды.** `lastDone()` — это последний
элемент, «ни разу не выполнялась» — пустая история. Отдельных полей
`lastDone`/`neverDone` больше нет: раз их нельзя хранить по отдельности,
их нельзя и рассогласовать. Это ровно тот класс дефектов, который
устранялся выше (п. 4).

Экран «5. История выполнений» в карточке задачи показывает список отметок
(свежие сверху) с интервалом до предыдущей, а также сколько раз задача
выполнялась и каков обычный интервал между выполнениями — с разбросом
от минимума до максимума. Оттуда же можно вписать выполнение задним числом
(встанет на своё место по дате) и удалить ошибочную отметку.

Это описание того, что происходило на самом деле, а не расписание:
приложение по-прежнему ничего не планирует и не считает задачи просроченными.

Защита та же, что и у остальных данных: не больше `MAX_HISTORY = 5000` отметок
на задачу, метки времени приводятся к 1970–2100, порядок восстанавливается
при загрузке (внешняя правка файла увела бы интервалы в минус), даты в будущем
не принимаются. Удаление всех отметок корректно возвращает задачу в «никогда».

## Что осталось на потом

Не делалось намеренно — это развитие, а не дефекты:

- **Сортировка и фильтрация.** Список строго в порядке добавления, колонки досок
  тоже. Для трекера давности напрашивается «сначала самые давние».
- **Поиск по названию.** Секция `// ПОИСК / СБОР` существует с первой версии.
- **Перенос задачи между ветками** дерева.
- **Ширина в ячейках терминала** вместо кодовых точек — если появятся эмодзи.
